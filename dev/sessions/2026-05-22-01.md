## Accomplished

### (a) B2 cache bug — FIXED, committed `86fb953`

Root cause: `compute_infnorm` (`src/scaling/infnorm.rs`) returns
`ScalingInfo::Applied`, byte-identical to the MC64-complete `Applied`.
The B2 population gate was `matches!(scaling_info, Applied)`, so on an
InfNorm-routed matrix B2 cached the **InfNorm** vector and re-injected a
*stale iter-k* InfNorm scaling as `ScalingStrategy::External` on the
next warm `factor()`.

Fix (`src/numeric/solver.rs`): added an `mc64_ran` gate — B2 populates
only when the effective strategy is `Mc64Symmetric`, or `Auto` routing
(via `pick_scaling_strategy`) to `Mc64Symmetric`, **and**
`scaling_info == Applied`. `InfNorm`/`Identity`/`External` never
populate; on a non-MC64 route any prior cache is cleared.

Evidence:
- New test `mc64_cache_does_not_engage_on_infnorm_route_issue_49`
  (factors `tridiag(6,10,1)` 3× on one `Solver`; asserts route is
  `InfNorm`, `mc64_cache_hit_count()==0`, `symbolic_call_count()==1`) —
  fails pre-fix, passes after.
- `probe_cache_sequence` over all 10 dumped ex4_2_320 IPM iterates:
  `mc64_hits` 3/10 → **0/10**.
- All 23 solver tests + full `cargo test` suite green; `cargo fmt` /
  `clippy` clean; pre-commit hooks passed.
- `CHANGELOG.md` `[Unreleased]` updated (`### Fixed — B2 scaling cache`).

### (b) POUNCE-feral cost gap — investigated, premise refuted

The "~40 s/iter" premise is **wrong**. Clean measurements:

| Run | Wall | per-factor |
|---|---|---|
| ex4_2_320 → convergence (17 iters) | 10.6 s parallel / 17.5 s serial | ~0.5 s / ~0.9 s |
| ex4_2_160 → convergence (21 iters) | 2.29 s | ~0.09 s |
| 12-run repeat batch | parallel 10.2–10.8 s, serial 16.9–17.7 s, all exit 0 | — |

Per-factor ~0.5 s parallel is fully consistent with standalone feral
(~0.25–0.3 s warm). There is **no systematic gap** — POUNCE's wrapper
rebuilds `CscMatrix::from_triplets` each `factor()` but the symbolic and
pattern caches stay engaged (`symbolic_calls = 1`).

**One unexplained timeout — NOT a demonstrated feral bug.** One uncapped
convergence run timed out at 600 s, last printed line iteration 10. It
was never localized — the log simply stopped; whether it hung inside a
feral factorization, inside POUNCE's own step computation, or on a
system transient was not established. It did not reproduce:

- `probe_hang_loop` (new, `src/bin/`): **1000** back-to-back parallel
  factorizations of the densest dumped KKT (`ex4_2_320_009`) on one
  warm `Solver` — **0 hangs, 0 spikes** (median 277 ms; worst 1095 ms =
  the cold call-0 symbolic).
- 12 full POUNCE runs (6 parallel + 6 serial): 0 hangs.

The earlier framing of "a real intermittent parallel-factorization race
in feral" was an **overclaim and is retracted**: a single unreproduced,
unlocalized 600 s timeout is not a demonstrated feral defect. feral
parallel factorization is value-deterministic — a fixed matrix does not
hang (1000× confirms).

**Nondeterminism IS present — ULP-level, upstream of feral.** Comparing
iteration logs across four POUNCE ex4_2_320 runs (`pounce_ts`,
`pounce_conv`, `pounce_ab`, `pounce_iter11`): every printed digit on
every iteration line matches **except** iteration 4's primal
infeasibility — `7.32e-13` in two runs, `7.33e-13` in the other two.
`max_iter`/`--dump` flags cannot change iter-4 arithmetic, so this is
genuine run-to-run variation (~1e-15 absolute), the fingerprint of
order-dependent floating-point summation. (An earlier note in this
session's journal §10:10 calling the logs "bit-identical to 7 figs" is
**wrong** and is corrected in §12:10.)

feral is *not* the source: feral factorization is value-deterministic —
1000 identical factorizations of a fixed matrix (probe above) confirm
fixed input → fixed output. The nondeterminism enters **upstream**, in
POUNCE's KKT assembly or constraint/derivative evaluation.
HashMap-ordered iteration is the classic Rust cause of order-dependent
summation; POUNCE uses `HashMap` in its `.nl`/Hessian-tape code
(`pounce-cli/src/nl_tape.rs`, `nl_hessian_program.rs`, `nl_reader.rs`),
so the HashMap hypothesis is evidence-backed — though the exact code
path was not traced this session.

**The 600 s timeout remains n=1.** The ULP nondeterminism above is
normally harmless (all 12+ runs still converge in 17 iters). Whether it
can *occasionally* perturb a near-singular KKT enough to tip feral's
pivoting into the known deterministic #44/#46/#48 cascade is plausible
but **unproven** — the lone 600 s timeout is one unexplained,
unlocalized event and is not asserted to be connected. POUNCE #44
(BLEACHNG, n=17) documents the same fast-vs-hang symptom class; at n=17
feral's parallel path cannot be the cause, which independently points
the nondeterminism source upstream of feral.

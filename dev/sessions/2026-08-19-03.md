## Accomplished

### The report is real, and it is purely a scheduling bug

The reporter serialized the tree-parallel solve with `FERAL_CB_THRESH`
and recovered 7.35 s of 49.41 s (15%) plus ~3.0M involuntary context
switches, on 14 cores over 100 IPM iterations. Two things follow that
the issue does not state:

1. `FERAL_CB_THRESH` does not choose the solve *core* — since #177 that
   is `cb_core_profitable`, which reads neither the worker count nor the
   environment. A huge threshold collapses the plan to one task, so the
   **same** CB core runs serially. The whole 7.35 s is scheduling
   overhead, and fixing it cannot move a bit of any solve.
2. Rows 3 and 4 of the reporter's table are within noise, so the CB core
   running serially already matches switching parallelism off entirely
   on this problem. Nothing in the report argues for changing which core
   runs.

### Mechanism: the overhead is per front, not per task

`cb_run_parallel` takes the shared `contribs` mutex inside its per-front
loop — once per child drained, once to store the front's own block. That
cost scales with the supernode count; `MIN_TOTAL_COST` is a floor on
*total* work. `NARX_CFy` has 45,736 supernodes and a Lagrangian Hessian
of 19,851 nonzeros: it clears every shape term of the gate and spends
the solve synchronizing. Wide-and-thin is the shape that looks most
parallel-friendly to the old gate and loses.

### Fix: split the gate, add the missing half

    cb_gate_shape(fwd_seeds, total, max_local)   // the three old terms
    cb_sync_amortized(total, n_nodes)            // total >= 64 * n_nodes

`CbTaskPlan::worthwhile = shape ∧ amortized`. `cb_core_profitable` — the
host-independent predicate that picks between the two numerically
distinct cores — applies **the shape half only**, so which arithmetic a
factor solves with is unchanged on every matrix (#177's contract).
`cb_core_profitable_matches_the_plan_gate` now pins the shape half, the
part the two implementations genuinely share.

64 cost units per front (`nrow·(nelim+1)`, about an 8×8 front) is the
measured break-even — see below.

## Decisions Made

- The CB gate has two halves; the overhead half is scheduling-only and
  must never reach `cb_core_profitable` (appended to `dev/decisions.md`).

## Abandoned Approaches

- The per-seed floor issue #175 suggests (`total / fwd_seeds`): the
  measured *winner* has the least work per seed of the three points, so
  a floor that rejects `NARX_CFy` rejects `poisson_160` first.
- Calibrating through `solve_sparse_refined_cb`: residual sweeps and
  per-call workspace construction are O(n) in both arms and hid the
  effect (1.00-1.02 reported where the pooled core shows 1.16-2.11).

Both appended to `dev/tried-and-rejected.md`.

## Next Session Should

1. Re-run `issue175_cb_gate_calibration` on a many-core host. The
   constant is calibrated at 4 workers; the mechanism (contention on one
   mutex) predicts the break-even *rises* with worker count, so 64 may
   be too low on a 14-core machine — the direction that leaves #175
   partially open, not the direction that regresses winners.
2. Consider removing the per-front `contribs` mutex in `cb_run_parallel`
   outright: each slot is written by exactly one task and drained by
   exactly one parent, ordered by the pending counters, so a
   `Vec<UnsafeCell<Option<..>>>` with an `AcqRel` handshake would erase
   the cost this gate now avoids and let thin trees parallelize again.
   Needs its own safety argument and a `tests/cb_solve_parity.rs` pass.
3. The factorization task graph is a further 2.2 s (4.5%) on the same
   problem (#175's table row 3). `PAR_TASK_MIN_FLOPS` already has the
   right *shape* of term; recalibrate it against an IPM corpus with
   `feral-diagnostics`' `calibrate_par_min_flops` rather than one-shot
   solves.

# Session 2026-06-06-01

## Goal
Investigate issue #80 ("AMD ordering dominates first factor ~55s on pf22
n=2.8M") and implement the requested fix (a faster/bucketed AMD).

## Accomplished

### Root cause — issue #80's premise is wrong (it is MC64, not AMD)
- Production `OrderingMethod::Amd` dispatches to `feral_amd::amd_order`
  (`symbolic/mod.rs:569`), a full quotient-graph AMD with degree buckets
  (`feral_ordering_core::quotient_graph`). On real pf22 it orders in
  **0.276s** (`ncmpa=0`). The AMD kernel is **not** the bottleneck.
- The ~53s is the **`LdltCompress` preprocessor's MC64 matching**
  (`scaling::compute_mc64_cache` → `mc64::compute_matching`), which the
  per-stage profiler folded into the `ordering` stage timer. On real pf22:
  total symbolic 54.5s / `ordering` 53.6s; with `preprocess=None` total
  drops to **1.23s** (`ordering` 0.28s).
- The in-tree `src/ordering/amd.rs::amd_order` *is* O(n²), but it is **dead
  code** — only `permute_pattern` from that file is used. The first probe
  mis-targeted it; see `tried-and-rejected.md` (2026-06-06).
- Repro trap: MC64 only does real work on real values; `vals=1.0` makes
  symbolic ~1.5s and hides the cost.

### Landed: profiler attribution fix (`36d847a`)
- `symbolic/mod.rs` now records the preprocessor under its own
  `ldlt_compress` stage (+ `compress_pattern`/`expand_perm`); `ordering`
  measures only `run_external_ordering`. Test
  `ldlt_compress_recorded_separately_from_ordering`. No output change.
- Validated on real pf22: `ldlt_compress 63.06s`, `ordering 0.237s`.

### Research: MC64 gating (`48bb238`, `dev/research/issue-80-mc64-preprocessor-cost.md`)
- MC64 fires from TWO decisions (LdltCompress preprocess + Mc64Symmetric
  scaling), both on the arrow signature; disabling one leaves the cost.
- Full-Solver A/B, pf22 (ref n_neg 940248) and pf01 (n_neg 126744):
  inertia EXACT in every config. Dropping MC64 (preprocess=None + InfNorm)
  is **27× faster** on pf22 (2.42s vs 65.5s), resid 3.8e-11 (fine). MC64
  scaling yields a spurious `Singular` on pf01; InfNorm is clean.
- MC64 cost ≈ O(n^1.9) (1.3s @ 366k → 63s @ 2.8M).
- Proposed a narrow large-powerflow MC64 gate; **deferred** as a
  decisions.md-level default flip pending a corpus validation sweep +
  intermediate powerflow sizes. Not implemented.

## Addendum (post-checkpoint work)

After the checkpoint above, two follow-on questions from the user led to the
**actual** fix and a cleanup:

### MC64 had an avoidable O(n·m) — FIXED (`6699f09`)
`hungarian_match` reallocated `IndexHeap::new(m)` inside the per-column
augmenting loop (O(m) zeroing × up to n columns = O(n²)). Hoisted the heap
out of the loop + incremental `reset(touched)`. **MC64 matching on pf22:
53s → 0.309s (~170×); default first factor 65.5s → 2.594s (~25×)**;
inertia 940248 and residual 5.28e-13 unchanged (bit-identical). This is the
real resolution of #80 and **supersedes the routing-gate proposal** — the
default config is now fast with MC64 still on, so no default-behavior change
is needed. Research note updated (§8).

### Removed dead `amd_order` (`10a3a1a`)
Deleted `ordering::amd::amd_order` (the O(n²) legacy trap) + tests +
helpers + two orphaned examples; kept `permute_pattern`.

### Net result for issue #80
First factor on pf22: ~92s (issue) → **2.6s**. Profiler now attributes the
preprocessor correctly. Issue comment posted with the corrected analysis.
The "next session should" dead-code item (#1 above) is **done this session**.

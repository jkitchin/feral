## Accomplished

### Review

Verified every claim in #154 against `808babb` (v0.15.0). The diagnosis is
correct and all line references are exact: `solver.rs:430` (`use_parallel:
true`), `:972` (unconditional `ensure_parallel_pool()`), `:1148`, `:1216`,
`:1540`, and the quoted `ensure_parallel_pool` body. Three gaps in the
proposal, all confirmed by measurement rather than reading:

1. **The test inventory was incomplete, and understated.** The issue names
   one test and calls it a latent flake. Applying *only* the issue's
   one-liner to a pristine tree and running under `taskset -c 0`:

   ```
   test result: FAILED. 404 passed; 3 failed; 6 ignored
     solver_parallel_default_is_on             solver.rs:2825
     solver_parallel_factor_matches_sequential solver.rs:3852
       assertion failed: par.parallel()
     solver_reuses_thread_pool_across_factors  solver.rs:2887
       .expect("pool must be built after first parallel factor")
   ```

   `solver_parallel_factor_matches_sequential` is the #7 bit-exactness
   regression test. Repairing only its assertion would leave it comparing
   the sequential driver against itself — passing vacuously, with the
   contract silently unchecked.

2. **The "filed separately" fallback bug is not separable.** After the
   default flips, `with_parallel(true)` — the escape hatch #154 recommends
   for wasm — still reaches `ensure_parallel_pool()` and, on build failure,
   falls to a `None` arm that runs the *parallel* driver bare, i.e. on
   rayon's global pool. That is the failure being avoided, reintroduced
   through the workaround prescribed for it. Shipping the default flip alone
   would release a version whose documented wasm answer is a trap.

3. **A fourth dispatch site the issue misses:** `solve_many_refined`
   (`solver.rs:1601`) has the same `None`-arm shape as `solve_refined`.

Adjacent sweep over every rayon entry point reachable from `Solver`:
`intrafront_parallel` (Lever 1.1) is set only inside the parallel driver
(`factorize.rs:3127`), so the sequential path never spawns nested rayon work
— the pounce#79 oversubscription guarantee holds, not a bug. `solve.rs`
rayon uses are all under `solve_sparse_refined_parallel`, already gated. One
real find: `ensure_parallel_pool` sized its pool with
`rayon::current_num_threads()`, which **initializes rayon's global registry**
as a side effect — spawning workers we never use, and on a host that cannot
spawn, failing inside rayon rather than at our own `build()` where we can
handle it.

### Implementation

- `Solver::default_use_parallel()` —
  `available_parallelism().is_ok_and(|n| n.get() > 1)` — now supplies the
  `use_parallel` default in `with_params`.
- `Solver::pool_num_threads()` replaces `rayon::current_num_threads()` in
  `ensure_parallel_pool`: `RAYON_NUM_THREADS`, else `available_parallelism()`,
  else 1. `Solver` no longer touches rayon's global registry on any path.
  Split into a pure `pool_num_threads_from(env, hardware)` so the precedence
  rule is testable without mutating process-global env from a threaded runner.
- All four dispatch sites (`factor()` initial, MC64 retry, `solve_refined`,
  `solve_many_refined`) now require flag **and** pool; the fallback runs the
  sequential driver instead of the parallel one on the global pool. The
  `solve_refined` comment that stated the global-pool fall-through as
  intentional is replaced with an explanation of why it was not.
- Doc comments corrected at the three sites claiming "Default `true`"
  (field `:263`, `with_parallel`, `parallel()` accessor), plus
  `ensure_parallel_pool`, whose doc claimed `build()` "only fails on bad
  `num_threads` configuration (e.g. zero) which we never pass" — refuted by
  the issue's wasip1 measurements.
- `FERAL_PARALLEL` (C ABI) gained a force-on arm (`1`/`on`/`true`/`yes`).
  It was off-only; with a derived default, a wasm-bindgen-rayon embedder
  otherwise has no way to opt in without a rebuild.

### Tests

Rule adopted: any test meaning "the parallel driver" constructs with an
explicit `with_parallel(true)`; only the default test asserts the derived
value, and it asserts against the same probe the constructor uses so it
cannot silently become environment-dependent again.

- `solver_parallel_default_is_on` → `solver_parallel_default_follows_platform`
  (covers `new()`, `default()`, and the probe itself).
- `solver_reuses_thread_pool_across_factors`,
  `solver_parallel_factor_matches_sequential` → explicit `with_parallel(true)`.
- New `pool_num_threads_precedence`.
- New `solver_parallel_without_pool_falls_back_to_serial_refine`: reproduces
  the post-build-failure field state (factor with parallel off so no pool is
  built, then flip `use_parallel`) and asserts `solve_refined` /
  `solve_many_refined` output is **bit-identical** to a sequential solver.

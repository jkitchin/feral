ROOT CAUSE of the apparent contradiction:
1. factor(_, None) can NEVER return WrongInertia (solver.rs:1271 gates it on
   check_inertia=Some). The issue's "status=WrongInertia" came from pounce's
   own inertia comparison, not the posted repro (which would print Success).
2. Numeric code is byte-identical between the issue's cited 2ef751f and HEAD
   (git diff 2ef751f..HEAD touches only src/symbolic/mod.rs, the n>100k #73
   ordering change, irrelevant to n=1103). So "reproduces on 2ef751f" should
   equal HEAD's 488. It does not -> the .mtx is not the exact thing pounce
   factored.
3. The .mtx is full-precision f64 (17 sig figs) but the matrix has dynamic
   range 1.6e-9 .. 4.7e13 (cond ~1e22, the mu~2.5e-9 vertex). The smallest
   SCALED pivot is 1.2e-12, i.e. ~2.5e-26 relative to ||A|| -- one eigenvalue
   at computational zero whose SIGN is set by the last ULPs of the assembly.
   A 1-ULP difference between pounce's live KKT assembly and the round-tripped
   .mtx flips that pivot's sign -> 488 vs 489. Both are "defensible" reads of
   a 0 eigenvalue; MA57 and feral-on-the-dump both say 488.

CONCLUSION: not a reproducible feral bug as filed. feral AGREES with MA57
(488) on the dumped matrix under every scaling/thread/warm-state config. The
489 is a knife-edge sign flip in pounce's live assembly that the .mtx round
trip does not preserve. To make progress we need pounce's EXACT in-memory
matrix bits (or to repro inside pounce), not the dump. Chasing 488->489 by
changing inertia classification on a ~1e-26-relative pivot would risk the
inertia gate (cf. inertia-near-singular-certification.md: a single isolated
~0 eigenvalue is provably invisible to BK pivot magnitude; the note already
rejected a trailing-norm rank criterion for exactly this reason).

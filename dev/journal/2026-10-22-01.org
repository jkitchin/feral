Question: why pounce's qcqp1000-2c LinearSystemFactorization (100.5 s,
163 it) is 1.8x the harness's 56.3 s on the same 164 dumped KKTs.
Measurements (sequential, crates.io feral 0.21.0, same machine):
- harness --reuse --serial on the 164 dumps: factor 75.9 s (parallel

- pounce 0.13 (9958a24e) --json-output: linear_solver.total_factor_secs
  100.81 s over n_factors 165 (n_pattern_changes 1), wall
  LinearSystemFactorization 105.5 s, total_delayed_cols 2 947 819,
  total_n_tiny 30 379, last_nnz_l 2 899 772. The harness on the same
  matrices: Σdelays 1 606 093, Σtiny 39 386, iter_163 nnz_l 1 969 680.
  pounce times only `self.solver.factor(matrix, None)` (pounce-feral
  lib.rs:1319), so the 100.8 s IS feral's factor — not timer scope.
  Same iteration log as the dump run (itdiff: identical over 164 lines).
- The 165th factor is the least-squares multiplier init solve before
  iter 0 (Ipopt LeastSquareMults: W = 0, D_x = D_s = 1, D_c = D_d = 0),
  which is not dumped. It is the first matrix the Solver sees, so its
  symbolic (Auto preprocess -> LdltCompress, whose MC64 matching is
  value-dependent) is cached and reused for all 164 IPM KKTs.
- Reconstructed that init matrix from iter_000's dump (W triplets -> 0,
  x/s diagonals -> 1, c/d diagonals -> 0) and prepended it:
  harness factor 98.98 s, Σdelays 2 948 051, Σtiny 30 378, iter_163
  nnz_l 2 899 772, del 16 628 — matches pounce's summary to the digit on
  nnz_l/last delays and within 0.01 % on totals. Reproduced.
- Same sequence with `Solver::invalidate_symbolic_cache()` after the
  init factor (harness --inval1): factor 56.39 s, Σdelays 1 606 314,
  inertia (6007,5107,0) on 165/165 in both runs.
Conclusion: the 44 s "integration gap" is the symbolic analysis being
taken on the LS-multiplier init matrix, a pounce-side call-order effect
with an existing feral API remedy (re-analyse once after the init
solve, or analyse on the first IPM KKT). Not a feral kernel cost and
not thread dispatch. No pounce source modified. Draft comment for the
pounce side (#224 thread / pounce issue):

  pounce's qcqp1000-2c LinearSystemFactorization gap (100.8 s in
  `total_factor_secs` vs 56.3 s for the same 164 KKTs in a fixed-matrix
  harness) is the symbolic analysis, not feral's kernel or the timer.
  The first `factor()` pounce issues is the least-squares multiplier
  init system (W = 0, D_x = D_s = I). feral caches the symbolic per
  pattern, and its default `OrderingPreprocess::Auto` picks
  `LdltCompress`, whose MC64 matching depends on the values; every
  later IPM KKT reuses the ordering chosen for that init matrix.
  Reproduction with crates.io feral 0.21.0: prepending the
  reconstructed init matrix to the 164 dumps gives 98.98 s, Σdelayed
  2 948 051, last nnz_l 2 899 772 (pounce: 100.8 s, 2 947 819,
  2 899 772); calling `Solver::invalidate_symbolic_cache()` once after
  the init factor gives 56.39 s, Σdelayed 1 606 314, inertia
  (6007,5107,0) on all 165 either way. Suggested pounce-side change:
  invalidate the symbolic once after the multiplier-init solve (or skip
  feral for it). The factors differ from what pounce computes today, so
  the trajectory may move at round-off level.

* 00:40 :issue-194:design:
Key design finding, not in the issue: supernode-boundary polling alone
would NOT fix the reported case. Issue #8 records that a delayed-pivot
cascade concentrates 118k delayed pivots into three ~14k-column expanded
root fronts — the 87 s factor is dominated by individual *fronts*, so a
between-supernodes check returns "5 s plus one 44 s supernode".

So poll at two places:
  1. supernode boundaries, in both drivers;
  2. the `while k < ncol_eff` panel loop in the dense frontal factor,
     which is one level out from the hot kernels (loop body is >= O(nrow)).

Mechanism `Option<Arc<AtomicBool>>` on `NumericParams` + a new
`FeralError::Interrupted`, so both drivers' existing error unwind
(sequential `?`, parallel `first_error` + task fast-exit) carries the
cancellation with no new control flow.

* 03:35 :issue-194:review:defect:
Review on PR #195 found a real defect in this session's work. Verified it
against the code before acting rather than taking the report on trust.

`Solver::factor`'s issue-#65 MC64 rescue matched the retry factorization's
result with a catch-all `_` arm, which absorbs `Err(_)` — including the
`Err(FeralError::Interrupted)` this session's polling introduced. Two
consequences:

1. `factor` returns Success/Singular for a cancelled call, contradicting
   the contract this branch publishes.
2. `mc64_retry_not_adopted` latches. Keyed on the *pattern* and cleared
   only on a pattern change, so an IPM refactoring a fixed pattern loses
   the #65 rescue for every remaining iterate — reporting unrescued
   inertia because of an unrelated cancellation. That is the inertia hard
   rule in CLAUDE.md, broken by a caller pressing stop.

The window is not a narrow race: it is the whole duration of the retry, a
second full factorization, i.e. exactly the long-factorization case #194
exists for. The latch's own doc already flags the interaction with the
inertia rule, but reasons about a *genuine* non-adoption, where "MC64 did
not help" is evidence. An interrupt arms it with no evidence at all.

Fixed on the branch as 7b42414 (author's own commit, pushed while this
session was preparing the same change): one arm before the `_`,
propagating `Interrupted` and leaving the latch disarmed, plus
`tests/issue194_interrupt_during_mc64_retry.rs`.

* 03:50 :issue-194:test-design:circular-detector:lesson:
Recording a false-green trap, because two independent implementations of
the regression test hit it — this session's and 7b42414's — which is
strong evidence it is easy to walk into rather than a one-off slip.

The test must place a watchdog inside the MC64 rescue. The rescue only
runs on the *first* factor of a pattern (it latches afterwards either
way), so the flag has to land inside a cold call. The obvious detector for
"did the flag land in the rescue?" is

: status == Interrupted && mc64_retry_attempt_count() == 1

and `status == Interrupted` is *precisely what the bug suppresses*. On
un-fixed code every trial therefore reads as "missed the window", the
sweep falls through to its skip-and-pass guard, and the test passes green
against the very defect it was written for. Observed directly here:

: 65% (359.9ms): missed the window — status Success, retry_attempts 1
: 75% (415.3ms): missed the window — status Success, retry_attempts 1
: SKIP: no watchdog fraction landed inside the MC64 rescue

Every one of those "missed" lines is the bug firing, reported as a miss.

Both fixes converged on the same repair: build the detector only from
signals that read identically with and without the fix.
`mc64_retry_attempt_count() == 1` proves factorization #1 returned
`Ok(..)` (the rescue gate keys on `Ok`, so an interrupt seen during
symbolic or factorization #1 would leave the count at 0), and a
before-return check on the watchdog store (a `done` flag here, `delay <
call_elapsed` in 7b42414) proves the flag went in while the call was
still running.

**Generalisable rule: a skip-and-pass guard must never be reachable
through the failure mode it guards.** This tree uses skip-and-pass widely
— fixture-gated tests, timing-gated tests — so the pattern is worth
auditing for elsewhere.

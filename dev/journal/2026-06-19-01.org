* 14:40 :alloc:lu-update:measurement:
Phase 0 of "does reducing allocation speed up the LU update path"
(dev/plans, measure-then-pool). Wrote tests/lu_update_alloc_probe.rs: a
counting #[global_allocator] wrapping System, snapshotting alloc/realloc/
byte counts in a window around ONLY the update loop (per-segment factor
excluded).

Result on in-tree casctanks fixture (m=2169, 3 widest-bump segments, 144
updates, 0 needs_refactor):

  total:      allocs=259808  reallocs=25382  bytes=18519872
  per-update: allocs=1804.2  reallocs=176.3  bytes=128610

Baseline wall-time (cargo bench --bench lu_update_trace): 12.351 ms for the
144-update chain = 85.8 us/update. (criterion's "-93.6%" is vs a stale saved
baseline from before v0.11.1 — irrelevant; the 12.35 ms absolute is the
number.)

Conclusion: ~1980 alloc-ops per update against an 85.8 us budget. Even at a
conservative 20–40 ns/op that is roughly half-to-most of the update time —
two orders of magnitude more alloc-heavy per unit work than the multifrontal
factorization churn (~17–23 allocs/supernode) the project already pooled
(FactorWorkspace). Unlike its sibling sparse_solve.rs (pooled via take_zeroed,
zero steady-state allocs), the update path pools nothing. GATE PASSED.

Caveat carried forward: pooling has been falsified twice here (multi-slot
contrib pool, arena refactor) when bookkeeping cost exceeded the malloc saved.
The decisive arbiter is the Phase-1 bench delta, not the count — so Phase 1
lands the highest-frequency sites first (per-pivot pivot_data clone :371,
per-target row_sub new_row :381) and measures the bench immediately; revert
+ record as falsified if it washes.

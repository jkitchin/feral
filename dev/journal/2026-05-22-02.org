* 11:00 :issue44:narx:gflops:headline:
New diag =diag_narx_kernel_gflops=: estimate dense-LDLᵀ flops per
supernode from (nrow,ncol), divide by the profiler's per-supernode
wall. Result:

  NARX_CFy_0000  whole loop  6.93 GFLOP / 878 ms ->  7.9 GFLOP/s
                 nrow>128    6.92 GFLOP / 834 ms ->  8.3 GFLOP/s
  NARX_CFy_0001  whole loop  0.45 GFLOP /  67 ms ->  6.6 GFLOP/s
  NARX_CFy_0002  whole loop  0.45 GFLOP /  66 ms ->  6.7 GFLOP/s

Largest single front (snode 41453, nrow=1877 ncol=77): 0.26 GFLOP
in 15.8 ms = ~16 GFLOP/s. Reference: a cache-blocked f64 GEMM is
50-90 GFLOP/s single-core on this CPU class. **feral's supernode
kernel runs ~3-10× below the blocked-GEMM ceiling.** That is the
#44 bottleneck — confirmed, quantified, feral-side.

Root cause (read of =src/dense/schur_kernel.rs=): the trailing
Schur update is =schur_panel_minus_*_strided= — a rank-n_elim
update done column-by-column (quad = 4 cols at once). No cache
tiling of the trailing block, no resident rank-k panel. For a
1800-wide trailing block that does not fit in cache the rank-k
panel (~1.15 MB for the big front) is re-streamed once per
4-column group → memory-bandwidth-bound. This is BLAS2.5, not a
cache-blocked BLAS3 GEMM (cf. faer's =lblt_blocked_step=, research
note faer-dense-speed-reference.md).

Secondary anomaly: several medium fronts are overhead-dominated,
not arithmetic-bound — e.g. snode 26043 (nrow=379 ncol=16) takes
~9 ms for ~2 MFLOP = 0.25 GFLOP/s. Worth a separate look; per-front
fixed overhead, not the kernel.

* 12:00 :issue44:narx:kernel-read:correction:
Read =src/dense/schur_kernel.rs= quad kernel + =factor_one_supernode=
(=src/numeric/factorize.rs:1991=). Two corrections to the 11:00 entry.

(1) The trailing-update kernel is NOT un-blocked BLAS2.5. The quad
kernel =schur_panel_minus_nofma_strided_quad= holds an m_r×n_r dst
tile (2 SIMD row-vectors × 4 cols = 8 accumulators) register-resident
across the entire rank-q loop; dst is loaded/stored once per chunk,
not once per q. It IS register-blocked, tuned for AVX2's 16 ymm.

(2) FMA is not a lever. =probe_fma_kernel= (issue #35) on this
aarch64 box: fma/nofma speedup 0.75-0.89 — the FMA path is a
*regression* on Apple Silicon. nofma is already the fast path.
Isolated kernel throughput: ~9-11 GFLOP/s (nofma, n_elim=64).

Revised ceiling estimate: the nofma path issues mul+sub (2 ops/madd);
M4 NEON nofma peak ≈ 30-35 GFLOP/s. Measured ~11 → ~1/3 of peak.
Realistic pure-Rust micro-kernel headroom is ~2-3×, NOT the ~10×
the GFLOP-vs-blocked-GEMM framing implied — feral cannot use BLAS
(hard constraint) and MA57's speed here is Apple Accelerate dgemm.

Remaining real levers, to be sized by microbench before planning:
- src-panel L2 re-read: the quad kernel processes only 4 trailing
  cols/call, so apply_blocked_schur_panel re-reads the whole rank-k
  src panel (~920 KB for a big front) ~450× → ~410 MB L2 traffic on
  one front. A wider n_r (8-12 cols/call) cuts that.
- NEON has 32 registers; the tile is sized for AVX2's 16. Wider
  m_r×n_r on aarch64 → more flops per src load.
- Overhead-bound medium fronts (snode 26043: nrow=379 ncol=16, 9 ms
  for ~2 MFLOP = 0.25 GFLOP/s) — 47× off the kernel rate. This is
  per-front fixed overhead, a separate mechanism from the kernel;
  needs its own probe.

* 13:00 :issue44:narx:kernel:neon-tile:committed:
Implemented the safe NEON-tile widening (plan
=dev/plans/quad-schur-neon-tile-widen.md=). =schur_panel_minus_nofma_
strided_quad= bulk loop now uses =const UNROLL = if cfg!(target_arch
= "aarch64") { 4 } else { 2 }= — unroll-4 on aarch64 (16 acc + 4 src
+ 1 splat ≈ 21 live, fits the 32-NEON budget), unroll-2 unchanged on
x86. Accumulators carried in =[S::f64s; UNROLL]= arrays; LLVM SROA
scalarizes them back to registers. Bit-exact: the unroll factor only
regroups body vectors into chunks, never reorders the q-ascending
accumulation chain. =schur_panel_minus_nofma_strided_quad_is_bit_
exact_vs_four_singles= passes (its len sweep hits body_len%4 ∈ 1,2,3).
Committed 5f1661c.

End-to-end NARX_CFy: ~3-7%. The gap between 2.4× and 3-7% means the

    scatter            0.1%
    extend_add        21.1%   <-- child->parent contrib scatter-add
    asm-residual       7.1%   (row_map populate/clear, F3.2b swap)
  densefactor       72.4%
    panelfactor        1.2%
    schur             43.5%   <-- the SIMD compute kernel
    scalartail         4.6%
    L-extract          0.5%
    contrib-extract   17.7%   <-- frontal->contrib copy
      zerofill         3.9%   <-- DEAD WORK (see below)
    df-residual        4.8%

Two measured findings:

(1) The contrib-block zero-fill is dead work. =contrib-extract= does
=contrib.resize(cdim*cdim, 0.0)= then a copy loop writing only the
lower triangle (ci>=cj). Read =extend_add= (factorize.rs:3425): it
reads =contrib.data[cj*cdim+ci]= only for ci>=cj — the SAME index set
the copy writes. Every cell read is overwritten by the copy; the
upper triangle is never touched. The =resize(_,0.0)= is 100%
removable. Measured cost: 3.9% of the loop (~44 ms). Smaller than the
earlier ~10% guess — the memset is bandwidth-bound and cheap relative
to the strided copy. Free 4%, no algorithm change.

(2) Contribution-block traffic is the #2 cost after the kernel.
extend_add 21% + contrib-extract 18% = ~39% of the loop is moving
contribution blocks (child->parent scatter-add, then frontal->contrib
copy). All O(cdim^2) memory traffic per front, NOT arithmetic. For
NARX's ~950 tall medium fronts (ncol 5-64, nrow up to ~1900) this is
the structural cost. schur is 43.5% — so kernel and contrib-traffic
are nearly equal halves of the loop.

Where to spend time, in priority order:
- contrib zero-fill: delete it. ~4%, trivial, provably safe.
- contrib-block traffic (~39%): the real lever. Needs a design look —
  packed-triangular contrib storage halves both the copy and the
  extend_add traffic; or fewer/bigger fronts. Not a micro-opt.
- schur (43.5%): kernel, already widened (5f1661c); BLAS-free ceiling
  limits further gains.

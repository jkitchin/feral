* 17:40 :issue1008:experiment:design:
First attempt at the decisive A/B was wrong and was killed after two instances.
I built discopt against PR #162 and compared "shipped dense =ftran=/=btran=" vs
"feral's sparse-rhs API". But PR #162 changes the *dense* entry points too — the
reach-limited sweeps — so that A/B had the reach route on in BOTH arms and
measured only the marginal value of the API. QPLIB_10063 read 33.56 s vs 33.41 s
and would have been reported as "the API is worth nothing".

Redesigned as a *three*-arm panel inside ONE binary (one feral, one discopt, one
md5), selected by env so the arms are seconds apart rather than separate builds:

- =off=   =DISCOPT_LU_HYPER_MAX_DENSITY=0=, dense entry points → feral's
  pre-#161 dense sweeps
- =reach= =...=0.10=, dense entry points → PR #162 change 1, no caller change
- =api=   =...=0.10=, sparse-rhs API → PR #162 change 2, caller changed

The cap knob is a new probe in discopt's =params()=. Proved it is actually read,
§6-style, rather than assumed: =DISCOPT_LU_HYPER_MAX_DENSITY=abc= panics with
"must be a float in [0, 1], got \"abc\"" out of the solver, so an arm cannot
silently degrade to the default.

The =api= arm is a genuine prototype of the caller change: =rho= comes from
=btran_sparse(&[(r, 1.0)])= and =alpha= from =ftran_sparse(sp.col(q))=, each
scattered into the same dense buffer the loop already allocated. The column-wise
PRICE and the Devex loop are untouched, so the delta is the solve and nothing
else — and it is a *lower* bound on a full hyper-sparse caller, which would also
drop the two =vec![0.0; m]= allocations and price row-wise.

* 18:20 :issue1008:tried-and-rejected:symbolic-reuse:
Tried the obvious cheap fix for a 32%-of-loop symbolic analysis:
*cache the ordering and reuse it across refactorizations.*  feral
permits it -- =SparseLu::factor= validates only =symbolic.m=, not the
pattern, so a stale ordering is a legal column order for a later basis
-- and the docs advertise reuse "across numerically different but
structurally identical bases".

It is catastrophic.  QPLIB_3775, =DISCOPT_LU_SYM_REUSE=1= on top of
=tri=1=:

  tri=1 reuse=0   wall   1.193 s     64 factorizations, LuNumeric   164.7 ms
  tri=1 reuse=1   wall 137.835 s   1112 factorizations, LuNumeric 18381.3 ms
  tri=0 reuse=1   did not finish within a 300 s timeout

=LuSymbolic= does drop to 0.82 ms total, exactly as intended, and it
buys a *115x slowdown*.  A simplex basis is not structurally stable
across 64 pivots: the stale ordering produces enough extra fill that
the Forrest-Tomlin update stops holding and the loop refactorizes 17x
more often, at 111x the numeric cost.  The reuse contract in the feral
docs is real but its precondition ("structurally identical") is exactly
what a simplex violates.

Rejected.  The ordering has to be *recomputed* every refactorization;
what it must not be is *expensive*.  That points at the ordering choice
(#163's revert), not at caching.

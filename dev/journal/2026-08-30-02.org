* 09:20 :refine:backward-error:bug:
`backward_error` (src/numeric/solve.rs) skipped any row whose `term` was
`NaN`, because `term > omega` is false for `NaN`. An overflowed iterate
makes every row `NaN` (|r| and d both reach inf, ratio is NaN), so the
function returned `omega = 0.0` — a diverged solve certifying itself as
exactly backward stable. Under `StopCriterion::BackwardError(t)`, newly
public in this PR, `reached()` is then true on the first test: the loop
breaks immediately and returns `RefineStop::Converged` with a garbage
iterate and `relative_residual = NaN`.

Evidence, with the guard removed:
: non-finite iterate [inf, 1.0] must report inf, got 0e0

The historical `EpsSqrtN` rule does not have this hole (`NaN < threshold`
is false, so refinement keeps running) and the shipped conjunction default
is covered by its normwise half, so only the bare `BackwardError` option
is exposed. Fixed by returning `f64::INFINITY` for any row where `d` or
`r[i]` is non-finite, guarded before the `d == 0.0` branch. Regression
test `backward_error_reports_infinity_on_a_non_finite_iterate` covers
inf/NaN/-inf iterates.

* 10:05 :solve:workspace:alloc:
`SolveManyWorkspace::for_factors` allocated `y`/`w`/`acc` at
`padded_ldw(nrhs) = nrhs.div_ceil(8)*8` unconditionally, while
`solve_sparse_core_many_into` only uses that stride when
`nrhs >= blas3_nrhs_threshold()` (32); below it the buffers are sliced
at `ldw = nrhs` and the padding is never touched. So the over-allocation
is worst exactly in the IPM regime: 8x on `nrhs = 1`, 4x on `nrhs = 2`.
On pounce's 126,028-row KKT that is 1 MB of `y` allocated as 8 MB, same
on `w`, rebuilt per refinement step. Invisible to the corpus benchmarks,
which run large `nrhs` where padding is exact.

Fixed by sizing on the same predicate the solve dispatches on, keeping
the unconditional padding only under `cfg!(feature = "kernel-probe")`
where the threshold is a runtime override that can move between
construction and use. The two must agree since the solve slices at
`n*ldw` / `nrow*ldw` / `ldw`.

* 22:05 :api:refine:issue190:downstream:
Answered the open downstream question on PR #191 ("Does =RefineOutcome=
carry the achieved residual / ω as well as the step count?") by
implementing it rather than just replying. It carried =steps=,
=relative_residual=, =stop= — ω was computed at every construction site
and dropped on the floor.

Added =RefineOutcome::backward_error=. The case for doing it now rather
than in 0.19.0: =RefineOutcome= is new and unreleased in this PR, so the
field costs no additional break, whereas adding it after release costs
one. And 0.18.0 makes ω *the thing the default criterion certifies* — a
host that gets =Converged= back currently cannot see the certificate
without a second =abs_symv=.

The one real design question was the not-measured sentinel. ω is only
formed when it is the criterion (=wants_omega=); otherwise =best_omega=
sits at the never-read =INFINITY=. Exposing that directly would report a
=EpsSqrtN= run that converged fine as ω = inf, i.e. catastrophic. So the
field is =NaN= when not measured, and the gate is on =wants_omega=, NOT
on =best_omega == INFINITY= — because since this session's earlier fix,
=INFINITY= is a *real* measurement (non-finite iterate) and must survive.

Five construction sites plus =aggregate_outcome= (now takes =best_om= and
=wants_omega=) plus the separately written narrow-path fold in
=Solver::solve_many_refined_into=, which needed its own =any_om_nan=
guard: a max fold over NaN silently yields 0.0, which would read as a
*perfect* backward error on a run that never formed ω.

* 23:10 :review:pr195:mc64:inertia:
Reviewing #195 (cooperative cancellation). Found one substantive defect,
in `Solver::factor`'s issue-#65 MC64 rescue at solver.rs:1359-1373:

    match retry {
        Ok((rf, ri)) if ri.zero < first_zero => { ...adopt... }
        _ => { mc64_retry_not_adopted_now = true; Ok((factors, inertia)) }
    }

The `_` arm absorbs `Err(_)`, so if the caller's flag is observed during
the *retry* factorization the resulting `Err(FeralError::Interrupted)` is
swallowed twice over:

1. `factor` returns Success/Singular, not Interrupted -- contradicting the
   PR's own published contract ("the first observation of true aborts the
   factorization").
2. `self.mc64_retry_not_adopted` latches. That latch is keyed on the
   *pattern* and cleared only on pattern change (solver.rs:1038), so in an
   IPM -- fixed pattern for the whole solve -- one unrelated cancellation
   permanently disables the MC64 rescue for every remaining iterate. The
   field's own doc-comment (solver.rs:252-273) flags this latch as
   interacting with the inertia hard rule: suppressing the retry reports
   "unrescued inertia where the pre-latch code recovered."

So a cancellation, which is supposed to be side-effect-free, can cause
wrong inertia for the rest of a solve. Fix is one arm before the `_`:
propagate `Err(FeralError::Interrupted)` and do not arm the latch. A
cancellation is not evidence that MC64 does not help -- the retry never
finished.

Verified the rest of the mechanism is sound: the ordering escalation at
solver.rs:1558 is on the `Ok` path only, so Interrupted cannot drive the
recursive re-factor; `run_parallel_task`'s `task_res = Err(..); break`
lands in the existing Err arm (factorize.rs:3919) which sets `first_error`
and skips the parent enqueue, and `break` (not `return`) keeps the
`local_contribs` restore into the workspace.

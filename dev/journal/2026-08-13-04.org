* 20:00 :issue164:design:
Read both solve paths before designing. The dense route
(=sparse_solve.rs=) already has the shape the sparse route needs: =reach_cap()=
turns =hyper_sparse_max_density= into a node budget, and =ReachWork::push=
*abandons the DFS the moment it exceeds the budget* rather than completing a
reach it is going to throw away. The sparse route (=sparse_hyper.rs=) has no
such bound anywhere.

First design (issue #164's suggestion, "skip the sort and sweep 0..m") does not
survive contact with the code:

- the sweep must not write nonzeros into positions absent from =pattern= --
  that is the =O(touched)= reset list, and a nonzero outside it silently seeds
  the *next* solve. So a dense sweep has to mark as it writes, or mark
  everything up front.
- =u_solve_sparse='s singular guard is deliberately *narrowed* to rows the
  solution depends on (decisions.md 2026-08-13). Sweeping all =m= rows widens
  it, which would make =SingularBasis= fire or not depending on the density of
  an unrelated right-hand side. Trying to keep the narrowing meant a per-row
  "does this position matter" test that needs the reach I just abandoned.

Settled on a smaller shape instead: the four kernels already sweep whatever is
in =hw.order=, so the fallback only has to *fill =order= differently* -- natural
topological order over =0..m= (ascending for =L=, descending for =Lt=,
descending/ascending =uperm_inv= rank for =U=/=Ut=) instead of the sorted
reach -- and mark the whole accumulator so the reset list covers the sweep.
The kernels themselves are untouched, and the fallback's behaviour is then
*exactly* the dense entry points', guard width included, which is the thing it
is falling back to.

Cost of marking everything: reset becomes O(m) and the next kernel's DFS
trips the cap immediately. Both are O(m) in a regime where the answer is
already dense, and =over_cap= is monotone within a solve so it costs one
pop, not a re-walk.

The review's =apiX= number reproduces (1.066x now vs 1.061x then, same

prediction.** The review computed an "ideal guard" bound of 1.116x by
taking max(1, speedup) per instance — i.e. assuming the best a guard can
do is claw the regressing instances back to parity. Actual: 1.197x.

The bound was too low because the review's density column is the *mean*
density of alpha over the solve, and the guard routes per solve. Even on
instances whose mean alpha is nominally sparse, individual solves are
dense and the guard catches them; the <10% bucket went 1.174x -> 1.253x.
Nor does the mean-alpha column say anything about the btran side
(=rho = e_r^T B^-1=), which the guard covers too.

Dense bucket (alpha >= 10%), n=4: 0.839x -> 1.067x. Every regression is
gone; the worst instance on the whole panel is now 0.998x, i.e. parity.
QPLIB_2055, the extreme at 61.95% dense, goes 0.735x -> 1.024x, with the
guard alone worth 1.393x on it.

* 20:46 :tooling:bug:context:
=./dev/assemble-context.sh= has been silently failing in this worktree,
and =dev/context.md= was stale: it was stamped
=Generated: 2026-08-13T22:25:41Z= and named =2026-08-13-02.md= as the
latest session while 03 and 04 both existed on disk.

Cause: the hook sanity check tests =[ ! -x .git/hooks/pre-commit ]=. In a
*linked worktree* =.git= is a file, not a directory, so that path never
resolves and the branch always fires. It then runs =pre-commit install=,
which refuses ("Cowardly refusing to install hooks with =core.hooksPath=
set" -- correctly, since =core.hooksPath= points at the main clone's
hooks, which is exactly how this worktree's commits were getting
fmt/clippy-checked all session). Under =set -e= that non-zero exit killed
the script at line 31, before =OUT= is even assigned on line 37 -- so it
never wrote a byte and left the old file in place. Exit code 1, and the
only visible symptom is a WARNING that reads like advice rather than a
failure.

Fixed by resolving the hook directory properly: =core.hooksPath= when
set, else =git rev-parse --git-path hooks=, which handles both layouts;
and =pre-commit install= failures no longer abort the script. Now exits 0
and writes 352 lines naming session 04.

Worth noting the blast radius: any session run from a worktree since this
guard was added has been orienting off a stale =context.md= without any
signal that it was stale. The "Generated" timestamp is the tell -- it
should be checked against =date -u=, not trusted.
